# Архитектура и соглашения монорепы

Один git-репозиторий — много независимых ESP32-проектов. Правила ниже обязательны для каждого проекта.

## Структура репозитория

```
esp32_projects/
├── CLAUDE.md                 # правила для Claude Code (кратко то же, что здесь)
├── README.md                 # каталог проектов
├── docs/                     # общая документация для всех проектов
│   ├── conventions.md        # этот файл
│   ├── diagrams.md           # схемы кодом: ноутбуки, schemdraw, WireViz, Docker
│   ├── esp32-arduino-setup.md# Arduino IDE + пакет ESP32 + COM-порт (один раз на ПК)
│   └── new-project.md        # как завести новый проект
├── projects/                 # проекты, каждый — самодостаточная папка
│   └── <project>/
├── shared/                   # общий код (Arduino-библиотеки), только когда он нужен 2+ проектам
├── templates/project/        # шаблон нового проекта
├── templates/component.md    # образец описания компонента
├── tools/                    # скрипты монорепы: new-project.ps1, diagrams.ps1
│   └── diagrams/             # Docker-образ для схем (Dockerfile, requirements.txt)
└── .claude/agents/           # агенты Claude Code (с префиксом проекта)
```

## Структура проекта

```
projects/<project>/
├── README.md                 # что делает, схема потоков, порядок сборки, быстрый старт
├── CLAUDE.md                 # необязательно: специфика проекта для Claude
├── docs/                     # NN-тема.md, нумерация в порядке сборки
│   ├── diagrams/             # схемы: schematics.ipynb (исходник) + *.svg (результат)
│   └── components/           # описание каждой детали проекта + даташиты
│       ├── README.md         # индекс: компонент — что это — откуда
│       ├── <маркировка>.md   # одна деталь — один файл
│       └── datasheets/       # копии PDF: <Производитель>_<модель>.pdf
├── firmware/
│   └── <sketch>/             # скетч Arduino: имя папки == имя .ino
│       ├── <sketch>.ino
│       ├── config.example.h  # шаблон настроек (коммитится)
│       └── config.h          # реальные настройки (в .gitignore)
├── server/                   # необязательно: серверная часть в Docker
│   ├── docker-compose.yml
│   ├── Dockerfile
│   ├── .env.example          # шаблон (коммитится)
│   └── .env                  # реальные настройки (в .gitignore)
└── hardware/                 # необязательно: схемы сборки, фото, BOM
```

Обязательны `README.md`, `docs/` (с `docs/components/`) и `firmware/`. Остальное — по мере надобности.

## Компоненты

Каждая деталь, которую проект подключает к ESP32 (модуль, датчик, индикатор, микросхема, зуммер…), описывается в `docs/components/<маркировка>.md` **до или вместе** со схемой подключения. `docs/NN-*.md` ссылаются на это описание, а не дублируют его.

Состав описания (образец — [templates/component.md](../templates/component.md), пример — `projects/led_clock/docs/components/E20362-I-UA3.md`):

1. **Кратко** — таблица: производитель, тип, ключевые характеристики, корпус, откуда деталь (куплена / выпаяна с чего).
2. **Маркировка** — что написано на корпусе и расшифровка по частям.
3. **Контакты** — таблица «вывод → назначение → полярность/направление» и рисунок, как считать выводы (вид, где вывод 1).
4. **Как работает / внутренняя схема** — то, без чего не понять подключение.
5. **Какая комбинация что делает** — какие выводы/сигналы/команды что включают (для индикатора — какие ножки зажигают сегмент и цифры 0–9; для датчика — регистры/команды; для модуля — режимы).
6. **Напряжение и ток** — питание, логические уровни, токи, предельные значения, расчёт резисторов. Совместимость с 3,3 В ESP32 — отдельной строкой.
7. **Проверка** — как проверить деталь мультиметром или минимальной схемой; что уже проверено на этом экземпляре.
8. **Документы** — ссылки на даташиты (локальная копия + URL источника).

Правила достоверности:

- Значения из официального даташита именно этой детали — без пометок. Из даташита похожей детали, от продавцов, из форумов или собственной оценки — **явно помечать** («ориентир», «по описанию продавца», «предположительно») и указывать источник.
- Даташит кладётся копией в `datasheets/` (сайты производителей пропадают), рядом — ссылка на источник.
- Факты, проверенные руками (мультиметром, на макете), отмечаются в разделе «Проверка».

`hardware/` — про сборку конкретного проекта (общая схема, фото, BOM); `docs/components/` — про отдельные детали.

## Схемы

Распиновки, принципиальные схемы и схемы подключения — **картинками из кода**, не ASCII: Jupyter-ноутбук `docs/diagrams/schematics.ipynb` (schemdraw, WireViz) → SVG в `docs/diagrams/` → вставка в документы `![...](diagrams/<имя>.svg)`. Python запускается только в Docker (`./tools/diagrams.ps1`), на ПК ничего не ставится. Подробно: [diagrams.md](diagrams.md).

## Именование

| Что | Правило | Пример |
|---|---|---|
| Папка проекта | `snake_case`, латиница | `my_nfc`, `weather_station` |
| Скетч | `snake_case`, имя папки = имя `.ino` (требование Arduino) | `firmware/nfc_reader/nfc_reader.ino` |
| Документы | `NN-тема.md`, номер = шаг сборки | `03-firmware.md` |
| Агент Claude | `<project-kebab>-<роль>`; общий для монорепы — `repo-<роль>` | `my-nfc-webhook`, `repo-diagrams` |
| Docker compose | `name: <project>` в начале файла | `name: my_nfc` |
| Контейнер | `container_name: <project>-<сервис>` или с префиксом проекта | `nfc-webhook` |

## Независимость проектов

- Проект не ссылается на файлы другого проекта. Общий код — только через `shared/`.
- Каждый проект собирается и запускается из своей папки, не трогая соседей.
- Ссылки в документации проекта — относительные внутри проекта; на общие доки — `../../docs/...`.

## Секреты

- Wi-Fi, ключи API, токены — только в `config.h` (прошивка) и `.env` (сервер). Оба в корневом `.gitignore`.
- В репозиторий кладём шаблоны `config.example.h` / `.env.example` с заглушками (`YOUR_WIFI_SSID`, `change-me`).
- Скетч проверяет наличие конфига: `#if __has_include("config.h") ... #else #error ...`.

## Прошивка

- Плата по умолчанию: **DOIT ESP32 DEVKIT V1** (`esp32:esp32:esp32doit-devkit-v1`), пакет **esp32 от Espressif** 3.x.
- Среда: Arduino IDE 2.x или `arduino-cli`. Установка один раз: [esp32-arduino-setup.md](esp32-arduino-setup.md).
- В шапке `.ino`: назначение, плата, библиотеки, откуда брать конфиг. Строка `#define FIRMWARE_VERSION "x.y.z"`.
- Все настраиваемые пины и тайминги — в `config.h`, с безопасными значениями по умолчанию через `#ifndef` в скетче.
- Пины: 6–11 не трогать (флеш), 34–39 — только вход. 0, 2, 5, 12, 15 — strapping-пины: не вешать на них внешние цепи, которые тянут уровень при загрузке (встроенный LED на 2 — можно).
- Serial — 115200 бод, понятные префиксы в логе: `[WiFi]`, `[HTTP]`, `[NFC]`.

## Серверная часть (Docker)

- Файл `docker-compose.yml` начинается с `name: <project>`: иначе compose берёт имя папки (`server`) и проекты столкнутся.
- Порты на хосте — из реестра ниже, настраиваются через `HOST_PORT` в `.env`.
- Данные — в именованных volume, не в bind-mount.
- Обязательный `GET /health` и `HEALTHCHECK` в Dockerfile.

### Реестр портов

| Порт | Проект | Сервис |
|---|---|---|
| 8090 | my_nfc | nfc-webhook |
| 8888 | tools | JupyterLab для схем (`tools/diagrams.ps1 lab`, только 127.0.0.1) |

Новый проект занимает следующий свободный порт (8091, 8092, …) и добавляет строку сюда.

## Документация

- Язык — русский. Команды — только для **Windows / PowerShell**, без Linux/macOS-вариантов.
- README проекта: одна строка назначения, схема потоков данных, ссылка «С чего начать» на `docs/00-guide.md`, дерево файлов, таблица «порядок сборки», быстрый старт.
- `docs/00-guide.md` — **путеводитель**: весь путь от деталей до работающего устройства по шагам, с чек-листами (`- [ ]`) и ссылками на подробные документы и их разделы; обязательно — чек-лист «проверка перед включением» и «если что-то не так → куда смотреть». Подробности в путеводителе не дублируются — только ссылки. Меняется порядок или появляется новый документ — обнови путеводитель.
- Документы нумеруются в порядке, в котором всё делается на практике.
- Отдельный `NN-troubleshooting.md` — таблица «симптом → причина → решение».

## Git

Репозиторий: https://github.com/rudenko-programmer/esp32_projects (`origin`).

### Ветки и Pull Request

- `main` — только рабочее, проверенное состояние. Напрямую в `main` не коммитим и не пушим.
- Любая работа ведётся в отдельной ветке от свежего `main` и попадает в `main` через Pull Request.
- Имя ветки: `<область>/<кратко-что>` латиницей через дефис: `my_nfc/forward-retry`, `weather_station/init`, `docs/setup-fixes`, `repo/ci`.
- После мерджа ветка удаляется.

```powershell
git switch main
git pull
git switch -c my_nfc/forward-retry
# ... работа, коммиты ...
git push -u origin my_nfc/forward-retry
gh pr create --base main --fill      # или ссылка, которую выдаст git push
# после ревью — Merge на GitHub, затем:
git switch main
git pull
git branch -d my_nfc/forward-retry
```

### Коммиты

- Формат: `<область>: <что сделано>` по-русски, в прошедшем или повелительном виде, без точки в конце.
  Области: имя проекта (`my_nfc`), `docs`, `shared`, `templates`, `tools`, `repo` (корневые конфиги).
- Один коммит — одно логическое изменение, по возможности в одном проекте.
- Автор коммита — только владелец репозитория. **Claude (и другие AI-ассистенты) не указываются** в соавторах: без `Co-Authored-By:` в коммитах и без подписей вроде `Generated with Claude Code` в описаниях PR.
- Перед коммитом проверить `git status`: `config.h` и `.env` не должны появляться.
